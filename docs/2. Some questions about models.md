
## `hidden_dim = 256` — why not 128 or 512?

This comes from the vulnerability detection literature directly:
- VulCNN (ICSE 2022) uses 256-dim embeddings
- ReGVD (ICSE 2022) uses 256-dim hidden states
- VulGAI (C&S 2023) uses 256-dim

The real reason it makes sense: CodeBERT outputs 768-dim. We have 3 branches × 256 = 768 fused. That means the fused vector has the **same dimension as CodeBERT's output** — it's not an arbitrary coincidence, it means we're not bottlenecking or over-expanding.

- 128 → too small, loses too much information from the graph and image
- 512 → fused would be 1536-dim, much heavier, no evidence it helps

---

## `max_length = 512` — why not 1024?

This one is **not a choice** — it's a hard constraint of the CodeBERT architecture. CodeBERT is built on RoBERTa which was trained with a maximum of 512 tokens. The positional embeddings only go up to position 512. If you pass more than 512 tokens, the model will throw an error.

Most C functions in Devign fit in 512 tokens. For the rare ones that don't, we truncate — this is standard practice in every CodeBERT-based paper.

---

## `num_layers = 3` (GAT layers) — why not 2 or 5?

From ReGVD and general GNN literature:
- **1 layer**: each node only sees direct neighbors — misses indirect data flow paths
- **3 layers**: each node sees up to 3 hops away — enough to capture most vulnerability patterns (input → intermediate → dangerous call)
- **5+ layers**: over-smoothing problem — all node embeddings start converging to the same vector, losing individual node identity

3 is the standard in GNN papers for code analysis. Specifically ReGVD uses 3.

---

## `Conv2d(3→32, kernel=3)` then `Conv2d(32→64)` — why these numbers?

- **3 input channels**: because we have exactly 3 centrality measures (degree, Katz, closeness). This is forced by the data.
- **32 then 64**: doubling is the standard CNN progression (proven in VGG, ResNet). 32 filters detect simple patterns, 64 filters detect combinations of those patterns.
- **kernel_size=3**: the universal standard. A 3×3 filter captures local neighborhoods. VulCNN uses 3×3.

---

## `AdaptiveAvgPool2d((4, 4))` — why (4,4)?

Different functions have different numbers of statements → different PDG sizes → different image sizes. A regular pooling layer would crash because it expects fixed-size input.

`AdaptiveAvgPool` always outputs exactly `(4, 4)` regardless of input size. Then `64 × 4 × 4 = 1024` → `Linear(1024, 256)`.

Why (4,4) specifically? It's a standard choice in image classification for the final spatial resolution before the classifier. (1,1) would lose too much spatial information. (8,8) would need a larger linear layer. (4,4) is the balance.

---

## `dropout = 0.3` — why not 0.5?

Standard in this domain:
- 0.1 → too little regularization, model overfits on small datasets like Devign
- 0.5 → too aggressive, the model can't learn properly
- 0.3 → used in VulCNN, VulGAI, and most similar papers

---

## `lr = 2e-5` for CodeBERT, `lr = 1e-4` for graph/image

The **2e-5** comes directly from the original BERT paper (Devlin et al., 2019). They recommend 2e-5, 3e-5, or 5e-5 for fine-tuning. Too high (1e-4) causes catastrophic forgetting — the model forgets what it learned during pretraining. Too low (1e-6) — it barely adapts.

The **1e-4** for graph and image branches is because they start from **random initialization**, not pretrained weights. They need a higher learning rate to learn quickly.

---

## `Linear(768, 256) → Linear(256, 1)` — the classifier

- 768 input: that's the concatenated fused vector (256+256+256)
- First layer compresses to 256: standard bottleneck design
- Second layer outputs 1 number: the logit for binary classification (vulnerable=1, safe=0)
- `.squeeze(-1)` removes the last dimension so shape is `(batch,)` not `(batch, 1)`

A two-layer MLP classifier is standard in all these papers. One layer would be too simple (just a linear separator). Three layers adds no measurable benefit.
